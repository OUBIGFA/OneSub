# Build and signed updates

`build-windows.ps1` reads product version `0.1.4` from
`apps/desktop/mygo.json`. The identifier `io.github.oubigfa.onesub`, update
public key and user-data directory remain unchanged. The installer is named
`OneSub-0.1.4-Setup.exe`. Use a numeric internal build number in
`yyyyMMddHHmmss` format.

## Signing key

The update public key is in `apps/desktop/mygo.json`. Keep its matching secret
outside Git, either in `.local/update-keys/mygo-update.key` or in
`MYGO_UPDATER_PRIVATE_KEY`. Back it up securely. Do not regenerate or replace it
for an ordinary build: installed apps trust this key. Do not put it in the
application, an artifact, a log or a pull request.

MyGo signs update archives with Ed25519. This is separate from Windows
Authenticode: the current installer is not Authenticode-signed.

## Build and test

Prepare the fixed runtimes, verify their hashes and stage only the reviewed
source files before building:

```powershell
./build/build-windows.ps1 -ReleaseTag '0.1.4'
```

This runs the repository checks and business-package unit tests in
`build/test.ps1` (the latter use `-CoreOnly`), the worker regressions
(`-WorkersOnly`), builds
the installer with MyGo and writes the fixed
local artifacts in `build/output/release/`:

- `OneSub-0.1.4-Setup.exe` and its `.sha256`;
- `onesub-0.1.4-windows-amd64.tar.gz` and its `.sha256`;
- `update-windows-amd64.json` and `build-info.json`.
- `OneSub-0.1.4-sbom.cdx.json` and its `.sha256`, generated by the pinned
  Syft cataloger from the actual package and verified production declarations.

Windows desktop, Windows 10, clean-machine, installation, upgrade, rollback
and uninstall acceptance are not build or release requirements. The default
entry does not start a private desktop or a virtual machine. Existing desktop
tests remain optional and require an explicit `-NativeDesktop` invocation.
The private-desktop launcher tests also require an explicit
`ONESUB_TEST_PRIVATE_DESKTOP=1` opt-in; repository discovery does not run them.
Do not describe unperformed Windows tests as passed.

Use `build/test.ps1 -CoreOnly -Packages './internal/media' -TestName '^TestH264'`
for a focused backend change. `-CoreOnly` without a package filter also runs
an explicit list of non-window application tests, including local MCP file
workflows, update checks and dependency boundaries. Use exact test names when
selecting tests in the application package; similarly named view tests may
require the optional native scope.

`build/test.ps1 -WorkersOnly` runs the real subtitle-format and SmartSub/libass
regressions without opening a window. It requires the prepared subtitle and
media runtimes and the locked style dependencies. Missing runtimes fail the
entry rather than silently skipping those checks.

The SBOM records packaged file SHA-256 values and source-tree/build identity.
It labels declarations separately from binary discovery and keeps incomplete
static-library coverage explicit. Generating a SBOM does not approve a Release.
The build-only Syft version and verified archive/binary hashes are recorded in
`third_party/manifests/sbom-tool.json`; keep it in the ignored toolchain cache.

`tools/finalize_update.py` preserves MyGo's archive and signature. It assigns
feed version `0.1.4.<build>` and an immutable `0.1.4` release URL when
`-ReleaseTag '0.1.4'` is supplied. Without `-ReleaseTag`, the channel is
`local-test` and the URL uses `build-<build>`. The build records the staged
Git tree and rejects unstaged, untracked or changed release source.
MyGo compares the numeric fourth component. SemVer `+build` metadata would not
order builds. Internal rebuilds do not change the product version, installer
name, installation identity or user-data directory.
Full archives are used; product-version deltas are disabled for these builds.

`build/test-updates.ps1` is part of the optional extended test entry. It uses a temporary key
and executable directory to test real MyGo signature verification, same-product
build ordering, refusal of invalid signatures and tampered archives, actual
file replacement and byte progress. It does not modify an installed OneSub.

## Local OneAsr runtime

The installer uses the pinned OneAsr v1.5.0 region-batch port, not a new inference engine.
`third_party/manifests/oneasr.json` records the source archive, patch, Cargo inputs and Rust 1.96.0 distribution checksums.
Keep the verified archives in `.local/downloads/` and the merged Rust compiler, Cargo, standard library, rustfmt and Clippy components in `.local/toolchains/rust1.96.0/`.
Visual Studio x64 C++ tools are required. A workspace containing spaces needs NTFS short names for the upstream resampler's CMake build.
Run `build/build-oneasr.ps1` to test and build this runtime; the Windows build calls it and reuses an exact verified match.
The port and its original-clock behavior are documented in `third_party/patches/oneasr/README.md`.

## Publish boundary

Building does not create a tag, upload files or publish a Release. Public
updates need a separately authorized, non-prerelease GitHub Release tagged
`0.1.4` for this version. The approved public attachment is only
`OneSub-0.1.4-Setup.exe`. Keep signed update archives, update manifests,
checksums, SBOMs, source materials and build records locally. Building does
not authorize uploading any of these additional files.

The app first checks the latest release's `update-windows-amd64.json`. When
that feed returns 404, it reads GitHub's latest stable release through the
same system proxy and compares the product version numerically. A newer
release containing the matching `OneSub-<version>-Setup.exe` offers a
**Download installer** action. The user downloads it in the browser and
installs it manually. The installer is never passed to MyGo's signed-update
installation path. A matching or older published version reports that the
app is current; a missing newer installer, network failure and cancellation
remain distinct outcomes.

Publishing an automatic-update feed still needs a separately approved
distribution location and matching signed archive. Automatic checking and
signed installation default on. Signed installation waits for an active
workbench task to finish, uses its cancellation/exit guards and never forces
a restart. The new build runs at the next launch. Builds predating the
installer-release check need one manual installation to receive this fix.
